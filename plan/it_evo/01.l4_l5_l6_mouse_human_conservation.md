# Plan: extend the L2/3 mouse–human archetype-conservation analysis to L4, L5 IT and L6 IT

## Context

`scripts/l23_evo/57.viz.human_jorstad23_mouse_b_ca_scores.py` and
`59.viz.mouse_cheng22_b_ca_scores.py` are the end of a chain that asks whether mouse L2/3 IT
archetypes have human counterparts: mouse archetype markers (Cheng22) are mapped through
1-to-1 orthologs and scored on human cells (Jorstad23), then rendered on both the human and
the mouse archetype embedding. If a mouse archetype is conserved, its score concentrates at
one human vertex.

We want the same evaluation for **L4, L5 IT and L6 IT**, with **L2/3 carried through the new
pipeline as a control**. The mouse half of the upstream work already exists in `scripts/it/`;
the human half does not exist at all for L4/L5/L6. The deliverable is a new sub-project
`it_evo` that reproduces the `18→58 / 01→05→08→56 / 60 / 57 / 59 / 26` chain for four
subclasses, driven by a `SUBCLASSES` config loop rather than four copies of every script
(precedent: `plan/it/50.yoo25_it_archetype_regulon_activity_heatmap.md`).

### Why L2/3 is in the loop

L2/3 is the only subclass with a known answer, so running it through the same code is what
makes the three new results interpretable. It tests two things at once:

1. **Pipeline equivalence** — the `it_evo` L2/3 outputs should reproduce the `l23_evo`
   56./58./60. record qualitatively, and its figure should reproduce
   `local_data/fig/l23_evo/57.human_mouse_b_ca_scores.pdf`.
2. **The normalization correction** — the mouse side will *not* be numerically identical,
   because `it_evo` reuses the `it/` varimax record, which normalizes cheng22 from `.raw`
   integer counts, whereas `l23_evo/18` double-normalizes the already-normalized `.X`
   (see G2). Whether the L2/3 conservation conclusion survives that correction is itself
   worth knowing, and the control is the only place we can check it.

### Decisions taken

1. Human cells: `Layer == 'All'` only, matching the L2/3 record.
2. A tracked prep script writes the three new per-subclass h5ads; they get symlinked into

3. Figures mirror 57/59 exactly: for NOC=3 two panels (Score B, and the C − A contrast); for
   NOC=2 (mouse L5IT) the single B − A contrast.

do this, so `VX2, VX6…` in the published human record means the same thing here.

`.X` is already log-normalized — use it directly, no `log2(CP10k+1)` step. Only the token and
input path are subclass-specific.

**L2/3 control:** this recipe is deterministic and identical to `l23_evo/01` + `05`, so

### `03.refine.human_jorstad23_it_num_archetype.py` + `03.refine.viz.…py`
NOC sweep 2–6 per human subclass, compute/plot split as in `l23_evo/08.refine`.

- **In** `02.human_<TOKEN>_varimax_coords.tsv`
- **Out** `03.refine.human_<TOKEN>_num_archetype_metrics.tsv`, `..._plotdata.pkl`;
  viz → `local_data/fig/it_evo/03.refine.human_<TOKEN>_num_archetype_{metrics,interactive}.html`

Params: `NOC_MIN/MAX=2/6`, `NREPEATS=10`, `N_OUTER=20`, `DOWNSAMP_P=0.2`,
`GROUP_COL='donor_id'` (the human precedent — `l23_evo/08.refine:38`).
Subclass-specific: `vx_cols` (from **Gate A**), hence `NDIM`.

**Two-stage structure — copy `l23_evo/08.refine` exactly; `run_noc_sweep` does not take the
bootstrap kwargs.** Its signature is `run_noc_sweep(sca, noc_grid, ndim, nrepeats, groups,
drop_pcs=None)`. It supplies `EV` and, via per-group `pcha_on_subset` refits, `ARV_rep`; its
second return value (plain-bootstrap ARV) is **discarded** in `08.refine`. The `ARV_mean` /
`ARV_std` columns come from a *separate* `N_OUTER` loop that calls
`sca.bootstrap_proj_pcha(NDIM, noc, nrepeats=NREPEATS, is_bootstrap=False,
downsamp_p=DOWNSAMP_P)` directly. Reuse `viz.py::{save_metrics_err_plot_html,
scatter_per_group_html}` unchanged.

**`NOC_MAX=6` is only meaningful if `NDIM` allows it.** `proj()` fits `PCA(NDIM+1)` and drops
one component, so the fit lives in `NDIM` dimensions and a non-degenerate simplex needs
`NOC ≤ NDIM+1 = len(vx_cols)`. If Gate A picks 4 VX columns for a subclass, NOC 5–6 are
structurally degenerate and their ARV blow-up carries no information. This is exactly the
pattern in the mouse sweeps: L4 and L6IT have `len(vx_cols)=4`, and their ARV explodes at
NOC=4–6. Note the bound next to each `vx_cols` entry.

**L2/3 control:** with `vx_cols = ['VX2','VX6','VX7','VX8','VX9','VX10']` this should reproduce
`l23_evo/08.refine.num_archetype_metrics.tsv` (ARV 0.021 / 0.040 / 0.418 at NOC 3 / 4 / 5).

## Gotchas

**G1 — `sample` vs `Sample`.** The cheng22 h5ad carries both columns with identical values
(verified), but `l23_evo/18/58` use `'sample'` while `it/19,21,23,25` use `'Sample'` — so the
reused `it/*_varimax_coords.tsv` files have a column literally named `Sample`. Script 05 must
set `SAMPLE_COL = 'Sample'` or the lookup `KeyError`s.

**G2 — cheng22 `.X` is already normalized; `l23_evo/18/58` treat it as raw counts.** Verified:
`X.max() = 6.40`, non-integer (log1p CP10k); `raw.X.max() = 1031.0`, integer, with identical
`var_names` and gene count. `it/19,21,23,25` correctly re-normalize from `.raw` — and those are
the scripts that produced the varimax loadings we reuse. So **scripts 05 and 09 must read
`m_adata.raw[:, m_adata.var_names].X`**, not `.X`. Copying `l23_evo/58` line-for-line would
silently mismatch the scale its own HVG loadings were fit on. Leave `l23_evo` alone — it is a
frozen record; note the discrepancy in script 05's docstring. This is the one place where the
L2/3 control is *expected* to diverge from the published numbers.

**G3 — `N_TOP_CELLS=300` is too large for the small mouse subclasses.** The L2/3 precedent draws
3×300 from 4,044 cells ≈ 22%. For mouse L5IT that would be 2×300 / 849 = **71%** and for L6IT
3×300 / 1,436 = **63%** — the "top" sets stop being archetype-pure and, since each is an
independent `argsort`, can even overlap. Use `n_top_cells` = **300 / 300 / 100 / 100** for mouse
L23 / L4 / L5IT / L6IT (≈22 / 19 / 24 / 21%); keep 300 for all human subclasses. Add fail-fast
assertions in 04 and 05: `noc * n_top_cells <= 0.25 * n_cells`, and pairwise disjointness of the
top-cell index sets.

**G4 — degenerate `cell_type` factors at Gate A.** Human **L6 IT has only 2 `WithinArea_cluster`
levels** (verified), a near-degenerate one-dummy design that makes its `cell_type` R² look
artificially small. Judge L6 IT primarily on *low donor + low source + low libsize* and say so
in the comment next to its `vx_cols`. (The mouse side already hit this: cheng22 L5IT has a
single `Type`, so `cell_type` R² is exactly 0 for all ten VX in
`local_data/res/it/23.cheng22_L5IT_vx_variance_partition.tsv` — its `VX_COLS` were chosen the
same way.)

**G5 — human gene identifiers are ENSG.** `var_names` are ENSG; symbols are in
`var['feature_name']` (verified: 29,352 unique, zero duplicates, so a plain dict map is safe).
Scripts 02/04/06/09 must key HVG lists and marker tables on `feature_name`, because the ortholog
table is symbol-based. Do not copy `it/21`'s `m_adata.var_names` line into the human script.

**G6 — stale categoricals after subsetting.** In the full file `WithinArea_cluster` is a
129-level Categorical; masking to `L4 IT` leaves 8 non-empty but all 129 categories present.
`pd.get_dummies` would then emit 121 all-zero columns and silently inflate the `cell_type`
design matrix. Script 01 must `remove_unused_categories()` before writing; script 02 should
fail-fast if any dummy column sums to zero. (The existing L2/3 file is already clean — which is
why the control would not have caught this on its own.)

**G7 — memory.** Never densify the 241k-cell file (~28 GB). Script 01 uses `backed='r'`.
Script 02 densifies one subclass at a time (L2/3 ≈ 5.5 GB, L4 ≈ 3.6 GB) and needs `del` +
`gc.collect()` between iterations. Scripts 04 and 06 should column-slice the sparse matrix to
the HVG / ortholog columns *before* `.toarray()`.

**G8 — seeding inside the loop.** `py_pcha` draws its furthest-sum start index and `S` init from
the *global* NumPy RNG and takes no seed argument. Re-issue `np.random.seed(PCHA_SEED)`
immediately before every `proj_and_pcha` call, or subclass #2's fit depends on how many draws
subclass #1 consumed — and the L2/3 control would stop matching `l23_evo/56` for a reason that
has nothing to do with biology.

**G9 — the two reference sweeps are not the same estimator.** Verified: `l23_evo/08.refine:70`
calls `bootstrap_proj_pcha(..., is_bootstrap=False, downsamp_p=0.2)` — 20% downsampling without
replacement — while `it/22.refine:67` calls `bootstrap_proj_pcha(NDIM, noc, nrepeats=NREPEATS)`
with the defaults, i.e. true bootstrap. They also group differently for `ARV_rep`:
`08.refine` by `donor_id` (3 groups), `it/22` by `Sample` (4 groups). So the human ARV numbers
script 03 produces and the mouse ARV numbers quoted at Gate C are **not on the same scale** —
judge each on its own elbow, never by comparing absolute values across the two.

**G10 — `NOC_mouse ≠ NOC_human`.** Script 09's matrices are rectangular; keep `l23_evo/26`'s
`n_mouse`/`n_human` parameterization rather than a single `NOC`.

**G11 — the `log2FC` divisor is wrong for mouse.** All eight marker scripts
(`l23_evo/21,25,56,58`, `it/33–36.follow`) share this line verbatim:
```python
log2fc_j = (X_in.mean(axis=0) - X_out.mean(axis=0)) / np.log(2)
```
Dividing by `ln(2)` converts a **natural-log** difference to log2. Verified that human `.X` is
`ln(CPM+1)` (reversing with `exp` gives median row sums 999,477 ≈ 1e6; with `2**` only
163,886), so this is correct for the human scripts. But the mouse `X_norm` is built as
`log2(CP10k+1)` — already base 2 — so the division **inflates every mouse log2FC by
1/ln2 = 1.443×**. With `LOG2FC_THRESH = log2(1.5) = 0.585`, the mouse marker filter effectively
admits genes at a true fold change of `2**(0.585*ln2) = 1.32×`, not 1.5×.

Fix in the new code: script 05 must **drop the `/ np.log(2)`** because its `X_norm` is already
log2. Script 09's `archetype_log2fc` is applied to both species from one function — it must
become per-species: divide by `np.log(2)` for human, not for mouse. Do **not** patch
`l23_evo` — frozen record — but state the correction in script 05's docstring.

Scope note: `l23_evo/26`'s headline metric is **Spearman**, which is rank-based, so a constant
1.443× on the mouse row leaves it unchanged. The marker-set side (Jaccard, hypergeometric) *is*
affected, via which genes clear the threshold. This bug is independent of G2 — same scripts,
different defect.
